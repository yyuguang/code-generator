# 项目名称

AI 业务系统生成器

# 项目背景

中后台业务系统开发中存在大量重复性的模块级 CRUD 开发工作，传统模式下从自然语言需求到统一技术规格、数据库设计、后端工程骨架落地之间存在较多人工分析、重复建模和模板复制环节，导致交付速度慢、风格不统一、错误率高。用户希望建设一个 AI 辅助代码生成平台，通过自然语言需求输入、结构化规格提取、规则校验、模板生成和工程导出，缩短从需求到代码的交付路径。

# 项目目标

1. 将自然语言形式的业务需求转化为统一、标准、可复用的结构化规格。
2. 基于标准规格稳定生成 Spring Boot Maven 后端工程代码与数据库脚本。
3. 通过规则校验与用户确认机制降低大模型幻觉造成的不稳定输出。
4. 提供在线预览与 ZIP 导出能力，支持开发人员直接下载、运行与二次开发。
5. 为后续扩展多模块建模、前端生成、知识库积累与多轮澄清预留能力。

# 用户角色

- 产品/业务提出者：以自然语言描述业务模块需求，希望快速得到可用工程骨架。
- 后端开发工程师：审阅并调整结构化规格，下载代码工程进行二次开发。
- 平台维护者：维护模板、规则、生成配置和后续扩展能力。

# 用户场景

## 场景 1：商品管理模块快速生成

业务或开发人员输入“商品管理模块”需求描述，系统解析模块、字段、操作和生成选项，用户修正规格后生成商品管理后端工程代码。

## 场景 2：订单管理模块骨架搭建

开发人员以自然语言输入订单管理需求，系统给出规格草稿和校验提示，用户确认后导出标准 Maven 工程作为开发起点。

## 场景 3：规格驱动的可追溯生成

开发团队将规格作为事实源进行复核、复用和版本迭代，在需求变化后修改规格并重新生成代码骨架。

# 功能需求

## FR-1 自然语言需求输入

### 描述
系统应提供自然语言需求输入入口，允许用户输入业务模块描述以及基础生成配置。

### 输入
- 业务需求文本
- 可选项目基础信息：项目名、包名、作者、模块名建议、生成选项

### 输出
- 可供 AI 解析的原始需求上下文

### 约束
- 第一版聚焦单业务模块输入
- 需要保留原始需求文本以便追溯

## FR-2 AI 结构化解析

### 描述
系统应调用大模型对自然语言需求进行理解与结构化抽取，生成标准规格草稿。

### 输入
- 原始需求文本
- 规格 Schema 与提示词约束

### 输出
- 结构化规格草稿（JSON 为事实源，可衍生 Markdown 视图）

### 约束
- 需输出模块名称、表名、字段、操作、生成选项等核心要素
- 需区分 AI 推断与明确提取内容

## FR-3 规格校验与修正

### 描述
系统应对结构化规格进行合法性检查，并对可自动修正的问题给出建议或标准化结果。

### 输入
- 结构化规格草稿
- 规则校验器与命名/类型约束

### 输出
- 校验结果
- 错误、警告、建议修正项
- 标准化后的规格数据

### 约束
- 需包含硬规则和软规则两类校验
- 不得将未确认推断伪装成用户已确认事实

## FR-4 规格审阅与编辑

### 描述
系统应允许用户在代码生成前审阅并编辑规格内容。

### 输入
- 结构化规格与校验结果

### 输出
- 用户确认后的最终规格

### 约束
- 第一版必须支持用户编辑字段信息、操作开关、表名与基础项目配置
- 需清晰标记 AI 推断、系统补全、待确认状态

## FR-5 模板化代码生成

### 描述
系统应基于确认后的统一规格，通过模板引擎生成后端工程代码与数据库脚本。

### 输入
- 已确认规格
- 模板与映射规则

### 输出
- 建表 SQL
- Entity
- DTO
- VO
- Mapper
- Service
- ServiceImpl
- Controller
- 基础接口文档内容

### 约束
- 生成器不能直接依赖自然语言，只能依赖标准规格
- 第一版聚焦标准 CRUD 骨架及基础分页/查询场景

## FR-6 工程装配与导出

### 描述
系统应将生成文件组装为标准 Spring Boot Maven 工程，并提供在线预览与压缩包导出能力。

### 输入
- 模板渲染结果
- 工程骨架模板

### 输出
- 标准目录结构的 Maven 工程
- 在线代码预览内容
- ZIP 下载包

### 约束
- 用户导出前应能预览文件树和关键文件内容
- 需支持重新生成，不直接污染历史结果

## FR-7 结果可追溯与可扩展

### 描述
系统应保留规格中心思想，支持后续扩展多模块、前端生成、知识沉淀与多轮澄清能力。

### 输入
- 当前单模块规格与生成记录

### 输出
- 可扩展的规格模型与工程结构设计约束

### 约束
- 第一版不实现复杂多模块关系，但规格设计必须预留扩展位

# 非功能需求

## 性能要求

- 单次需求解析和规格生成应在可接受时延内完成，满足交互式使用体验。
- 单模块代码生成与预览应支持秒级到可接受的短时等待，不应要求长时间后台处理。

## 稳定性要求

- AI 输出必须经过 Schema 和规则校验后才能进入后续流程。
- 对高风险规格错误应给出阻断提示，避免产出明显不可用代码。

## 可用性要求

- 用户主流程应简洁清晰，围绕“输入 -> 确认规格 -> 预览 -> 导出”展开。
- 规格编辑界面需让用户理解哪些内容来自 AI 推断、哪些来自系统补全。

## 可维护性要求

- 模板层、规则层、规格层应解耦，便于扩展不同模板和技术栈。
- 规格模型应支持未来的多模块、前端代码生成和知识库沉淀。

## 安全与合规要求

- 输入内容与生成结果需具备基础的错误处理和异常提示机制。
- 导出内容应避免直接包含未经校验的不合法标识符或高风险脚本。

# 边界范围

## 包含范围

- 单业务模块自然语言输入
- 统一规格 JSON 事实源与 Markdown 审阅视图
- 规格校验、用户编辑确认、模板生成、预览与导出
- Spring Boot Maven 后端工程骨架生成

## 不包含范围

- 多模块关联自动建模
- 复杂业务流程编排生成
- 前端页面代码生成
- 权限系统和审批流自动设计
- 全自动无需用户确认的黑盒生成模式

# 验收标准

## AC-1 需求到规格闭环可用

用户输入单模块自然语言需求后，系统能够生成结构化规格草稿，并支持用户在页面中查看和编辑。

## AC-2 规格校验有效

对缺失主键、非法字段名、非法类型、重复字段等问题能够给出错误或警告，不得静默通过。

## AC-3 代码生成产物完整

基于确认后的规格，系统能够生成 SQL、Entity、DTO、VO、Mapper、Service、ServiceImpl、Controller 及基础接口文档内容。

## AC-4 工程导出可用

系统能够将生成结果装配成标准 Spring Boot Maven 工程，支持预览与 ZIP 下载。

## AC-5 MVP 范围清晰

第一版仅面向单模块 CRUD 骨架生成，但规格模型与工程结构明确预留多模块扩展能力。

# 已确认技术架构

- 后端：Java 17、Spring Boot 3、MyBatis-Plus、Jackson、Lombok、Freemarker
- AI：大语言模型 API、Prompt 驱动需求解析、JSON 结构化输出
- 前端：Vue 3、Element Plus
- 数据存储：MySQL 8
- 部署：Docker、Nginx

# 未明确问题

1. 规格版本管理、历史记录与重新生成策略的持久化方案尚未细化。
2. 工程导出后是否附带可直接运行的数据库初始化与示例配置尚未明确。
3. 未来多模块扩展时的模块依赖表达方式尚未定义。
