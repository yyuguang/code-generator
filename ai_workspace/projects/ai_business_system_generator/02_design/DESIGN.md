# 系统概述

AI 业务系统生成器是一个面向中后台业务开发场景的规格驱动型代码生成平台。系统以统一规格中心为核心，将自然语言需求转化为可校验、可编辑、可追溯的标准规格，再通过模板引擎生成 Spring Boot Maven 工程代码与数据库脚本。

# 设计目标

1. 建立“自然语言 -> 规格 -> 代码”的稳定主链路。
2. 将大模型能力约束在“理解与提案”环节，避免直接黑盒产出工程代码。
3. 通过规则校验、用户确认和模板渲染提高可控性与可解释性。
4. 在单模块 MVP 范围内完成闭环，同时预留多模块、前端生成和知识沉淀扩展能力。

# 系统边界

## 系统内职责

- 接收自然语言业务需求与基础生成配置
- 调用大模型完成结构化规格草稿生成
- 对规格执行硬规则与软规则校验
- 支持用户审阅和编辑规格
- 基于最终规格生成 SQL 与 Java 工程代码
- 提供文件预览、工程组装与压缩导出

## 系统外职责

- 不承担复杂业务逻辑自动实现
- 不承担多模块关系自动建模落地
- 不承担前端页面生成之外的全栈低代码设计器能力
- 不替代开发人员进行业务规则最终确认与二次开发

# 总体架构

建议采用前后端分离的分层架构：

1. 前端表现层：基于 Vue 3 + Element Plus，负责需求输入、规格编辑、代码预览、导出交互。
2. 后端应用编排层：基于 Spring Boot 3，负责主流程编排、任务状态流转、调用下游服务。
3. AI 解析层：负责 Prompt 组织、模型调用、自然语言理解和结构化规格草稿输出。
4. 规格中心：负责统一规格模型、状态、版本视图与事实源管理。
5. 规则校验层：负责 Schema 校验、命名规范、字段类型、约束完整性检查与标准化修正。
6. 代码生成层：负责规格适配、中间模型转换与 Freemarker 模板渲染。
7. 工程装配层：负责标准 Spring Boot Maven 工程结构组装、打包与导出。
8. 基础设施层：负责 MySQL 8 持久化、Docker 容器化部署与 Nginx 反向代理。

# 模块划分

## MODULE-1 前端需求与预览模块
- 名称：Frontend Console
- 职责：提供自然语言输入、规格编辑、校验提示、文件树预览和导出操作。
- 输入：用户输入的需求文本、项目配置、规格编辑动作。
- 输出：解析请求、校验请求、确认请求、预览与导出请求。
- 依赖：后端 API。

## MODULE-2 AI 结构化解析模块
- 名称：AI Parsing
- 职责：调用大语言模型 API 将需求文本转换为结构化规格草稿。
- 输入：需求文本、规格 Schema、Prompt 模板。
- 输出：规格草稿与解析元信息。
- 依赖：模型网关、Jackson JSON 序列化能力。

## MODULE-3 统一规格中心
- 名称：Specification Center
- 职责：管理项目级、模块级、字段级、操作级规格及其状态。
- 输入：AI 规格草稿、用户编辑结果、校验结果。
- 输出：最终规格对象、Markdown 视图。
- 依赖：AI 解析模块、规则校验模块、MySQL 8。

## MODULE-4 规则校验模块
- 名称：Validation Engine
- 职责：执行硬规则和软规则校验，输出错误、警告、建议和标准化结果。
- 输入：规格草稿、规则配置。
- 输出：校验报告、修正建议、标准化规格。
- 依赖：统一规格中心、Jackson。

## MODULE-5 代码生成模块
- 名称：Code Generator
- 职责：将最终规格映射为模板渲染输入，生成 SQL 与 Java 代码文件。
- 输入：最终规格、模板配置、类型映射规则。
- 输出：生成文件集合。
- 依赖：统一规格中心、Freemarker 模板仓库、MyBatis-Plus 风格映射规则。

## MODULE-6 工程装配与导出模块
- 名称：Project Assembler
- 职责：组装标准 Maven 工程、生成文件树视图、打包 ZIP。
- 输入：生成文件集合、工程骨架模板。
- 输出：可预览文件树、导出压缩包。
- 依赖：代码生成模块。

## MODULE-7 部署与运行支撑模块
- 名称：Deployment Support
- 职责：提供容器化打包、静态资源发布和反向代理配置。
- 输入：前后端构建产物、部署配置。
- 输出：Docker 镜像、Nginx 配置、部署说明。
- 依赖：Docker、Nginx。

# 核心流程

## FLOW-1 从需求到规格

1. 用户在 Vue 3 前端输入自然语言需求与基础配置。
2. 后端调用 AI 解析模块，通过 Prompt 驱动大语言模型 API 输出 JSON 规格草稿。
3. 规则校验模块执行 Schema 与规则检查，给出错误、警告与修正建议。
4. 用户在规格确认界面审阅并编辑规格。
5. 统一规格中心保存最终规格状态为“已确认”。

## FLOW-2 从规格到工程

1. 代码生成模块读取最终规格。
2. 规格适配器将规格转换为模板友好的中间模型。
3. Freemarker 模板渲染器生成 SQL、Entity、DTO、VO、Mapper、Service、ServiceImpl、Controller 与基础文档内容。
4. 工程装配模块将生成文件与固定工程骨架组合成标准 Spring Boot Maven 工程。
5. 前端展示文件树与内容预览，用户触发 ZIP 导出。

## FLOW-3 部署与访问

1. 后端服务以 Docker 容器方式部署。
2. 前端静态资源通过 Nginx 托管并反向代理后端 API。
3. MySQL 8 提供规格数据、生成记录和平台配置持久化。

## 数据与部署

- MySQL 8
- Docker

# 技术选型说明

1. Spring Boot 3 + Java 17 作为平台后端主框架，满足现代 Java 应用开发与部署要求。
2. MyBatis-Plus 用于降低平台自身数据访问与后续生成代码风格的一致性成本。
3. Jackson 负责规格 JSON 序列化、反序列化与结构映射。
4. Lombok 用于减少平台后端样板代码。
5. Freemarker 作为模板引擎，负责 SQL 与 Java 工程文件稳定渲染。
6. Vue 3 + Element Plus 负责实现向导式规格确认与预览交互。
7. MySQL 8 承载平台规格、生成记录与配置数据。
8. Docker + Nginx 负责平台部署和前后端访问编排。

# 风险分析

## RISK-1 AI 幻觉导致规格不稳定

- 影响：可能生成不合法字段、错误命名或缺失关键约束。
- 应对：强制 JSON Schema、字段类型白名单、硬规则阻断、用户确认。

## RISK-2 规格模型过早耦合实现细节

- 影响：后续扩展多技术栈或多模块时改动成本高。
- 应对：引入规格适配层，将统一规格与模板输入解耦。

## RISK-3 用户误解平台能力边界

- 影响：期望系统自动生成复杂业务逻辑，导致体验落差。
- 应对：产品定位明确为标准业务骨架与基础 CRUD 生成平台。

## RISK-4 生成结果完整但不可运行

- 影响：平台可用性受损。
- 应对：在后续测试与发布阶段引入典型样例编译验证。

## RISK-5 模板与生成风格不一致

- 影响：平台自身使用 MyBatis-Plus，而生成代码若风格漂移会导致维护成本上升。
- 应对：在规格适配层中明确平台模型与生成模板模型边界，并统一生成约定。

# 设计决策记录

1. 统一规格中心作为平台唯一事实源，模板与导出环节只依赖规格，不依赖自然语言。
2. 第一版采用单模块 MVP，但规格数据结构按多模块扩展预留 `modules` 容器。
3. 用户必须在生成代码前审阅并编辑规格，避免纯黑盒生成。
4. 代码生成采用 Freemarker 模板驱动而非模型直接生成文件，以保证风格统一与可控性。
5. 前端采用 Vue 3 + Element Plus，后端采用 Spring Boot 3 + MyBatis-Plus，部署采用 Docker + Nginx。
6. 预览与导出分离，用户可先查看文件树和内容，再执行 ZIP 导出。
